# Sandbox

This is where invoice-ap runs for a test or an evaluation. It is not a customer environment.

Textract AnalyzeExpense is the default runner for the live read. Docling is the local backup. Both live in `../read_invoice.py`, which the command, the page, and this scorer share. The fields and the exception rule are in `../DESIGN.md`. The four numbers and how a set may change are in `../AGENTS.md`. A number that run did not produce is not a result.

`make_fixtures.py` writes `fixtures/*.pdf` and `labels.json`. It needs `reportlab`.

`make_hard.py` writes `hard/`. It does not rewrite that generated set. Scans and phone photos are those ten invoices rendered as images. Four more invoices use a second layout. Labels are `hard/labels.json`. Run it with `sandbox/.venv`, which has `reportlab`, `pymupdf`, and `pillow`.

`make_holdout.py` wrote `holdout/` once, on 2026-11-21, and refuses to run again. It is the generated holdout: 100 one-page invoices in twelve layouts the other two scripts do not produce, half clean PDFs and a quarter each scans and phone photos, with 25 that need an exception. Ten print payment terms and no due date; their labels follow the terms rule in `../DESIGN.md`, and each label says whether its due date was printed or comes from terms. The script was written without looking at any runner's output. The set is frozen: it is scored once per runner and never used to change a mapper, and a miss on it is reported, not fixed against it. `test_holdout.py` checks every file against the sha256 in `holdout/labels.json`.

`holdout-2/` is the second generated holdout, frozen on 2026-11-21. It was built by an agent working in an empty folder, with no access to this checkout, its runs, or the first holdout. `holdout-2/BRIEF.md` is everything it was told: the output format and the label rules from `../DESIGN.md`, and nothing about what earlier runs got wrong. It also says not to check its pages with any reader. Its generator, `holdout-2/make_set.py`, and its own notes, `holdout-2/NOTES.md`, came back with the set and are kept as provenance. The generator writes into the folder it runs in, so do not run it here. The set has 100 one-page invoices from 33 suppliers in 13 layouts: half clean, a quarter scanned, and a quarter photographed. It was delivered labeled to the narrow terms rule and relabeled on 2026-11-22 to the wider one by `relabel_holdout2.py`, which recomputes each due date from the terms in its label with a copy of the rule written apart from the reader, and prints counts and ids only. One invoice gained a due date. The PDFs are as delivered. 25 need an exception, and 47 take their due date from terms. It is scored once per runner, and a miss on it is reported, not fixed against it. `test_holdout2.py` checks every file against its sha256, rechecks the labels against the exception rule and the wider terms rule, and checks the rule copy on its published examples. Score it with `--labels holdout-2/labels.json`.

`holdout-3/` is the cross-border challenge set, frozen on 2026-11-22. It covers what holdout-2 cannot: day-first dates, decimal-comma amounts, and invoices in CAD, GBP, and EUR. It was built the same way, by an agent with no access to this checkout, from `holdout-3/BRIEF.md`. A first delivery failed the blind check, so the brief was amended and a fresh session built this set. The set has 120 one-page invoices from 54 suppliers in 20 layouts across nine countries. The first 60 came from that build. To widen the layouts, a supplement of 60 more with new suppliers and layouts was built from the same brief, sent back twice until it passed the same check, and merged by script on 2026-11-22. Each label's `part` says which build it came from. The supplement's generator, notes, and labels as delivered are in `holdout-3/supplement/`. About a fifth are US invoices for comparison, and every country appears clean, scanned, and photographed. Each label also records currency, country, date convention, and number style, so a run can be broken down by them. The labels follow the `foreign_currency` exception and the wider terms rule from the reader-misses spec, which the reader does not follow yet, so scoring it waits for that work. Its generator and notes are kept as provenance; do not run the generator here. `test_holdout3.py` checks the files and labels. Score it with `--labels holdout-3/labels.json`.

`make_practice.py` writes `practice/`, forty invoices for developing the reader-misses work. Each supplier prints dates and numbers in its own locale's format, taken from CLDR through Babel (en-US, en-CA, en-GB, de-DE, fr-FR, nl-NL, it-IT, es-ES), and the set covers USD, CAD, GBP, and EUR, decimal commas, payment terms in six languages including the forms the terms rule leaves for a person, due dates printed as words rather than dates, and the arithmetic exceptions. Its labels follow `foreign_currency` and the wider terms rule, the script's own copy. It needs `sandbox/.venv` with `reportlab` and `babel`, and DejaVu Sans for accented text. It is practice: not claimed, and it may be regenerated.

`make_inv_cdip_dev.py` writes the INV-CDIP development set: the 74 multi-page invoices the frozen set leaves out, page one only, under `inv-cdip/dev/` (ignored like the rest of `inv-cdip/`), with labels in `inv-cdip-dev.json` made by `get_inv_cdip.py`'s own rules. Run `get_inv_cdip.py` first.

`dev-crossborder/` is development data: holdout-3's rejected first delivery, unpacked once by `make_dev_crossborder.py`. The eight labels that broke the rules are dropped and listed. The agent's generator, notes, and labels as delivered are in `dev-crossborder/source/`. Its scans and photos are low resolution, which makes it a stress test.

`test_dev_sets.py` checks all three development sets.

`get_inv_cdip.py` fetches INV-CDIP, 350 real invoices from the UCSF Industry Documents Library labeled by Salesforce Research, into `inv-cdip/`, which git ignores. The documents are never committed. On its first run it wrote `inv-cdip.json`, the labels for the 276 one-page invoices, frozen on 2026-11-21; it will not write that file again. The set labels five fields (invoice number, invoice date, due date, tax, total), and each invoice is judged only on the fields annotated for it. Supplier and subtotal are not labeled, so the exception rule is not judged and the straight-through rate is recorded, not compared. The annotations are CC BY-NC 4.0: scoring and publishing results with attribution are fine, use in a paid offering is not. Attribution and the label rules are in the script and in `inv-cdip.json`. `test_inv_cdip.py` checks the labels and, once the documents are fetched, their sha256 pins. Score it with `--labels inv-cdip.json`.

`score.py --runner grok` or `score.py --runner claude` scores `labels.json`. `score.py --runner ollama` scores the same set with a local vision model. The default model is `qwen3-vl:8b`. That runner renders the page and sends the image to Ollama, so it needs `sandbox/.venv`. `score.py --runner docling` sends the file to Docling Serve at `127.0.0.1:5001` and reads the seven fields through `../read_invoice.py`. `score.py --runner textract --profile <aws profile>` sends each invoice to Amazon Textract AnalyzeExpense and maps its summary fields to the seven. It needs `sandbox/.venv`, which has `boto3`, and a signed-in AWS profile. The run file records pages and list-price cost per invoice, and a textract run is never overwritten. `score.py --runner hosted --url <reader url> --profile <aws profile>` sends each invoice to the deployed function instead, signed by `../host/call.py`, so the run scores the function that is running rather than this checkout. The URL can come from `INVOICE_AP_READER_URL`. Its run file adds the function's own read time, the HTTP errors, any invoice where the host's exception differs from the one the scorer recomputes, and cost: Textract per page plus an upper bound for Lambda. A hosted run is never overwritten either. Add `--labels hard/labels.json` to score the harder set. Add `--gate` to exit 1 when any field is wrong or the exception does not match the label. The run file is still written. The runs named in `../README.md` stay the claim. A run is written under `runs/`. An Ollama run on the generated set is named with the model. A Docling run on that set is named `YYYY-MM-DD-docling.json`. The call sees only that invoice.
